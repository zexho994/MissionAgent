# E2E 验收 — 迭代版本路线图

**日期**: 2026-05-13
**用法**: 每个迭代发布后,跑该迭代对应的所有用例,**全过 = 迭代验收通过**。失败一个,该迭代不能宣布完成。

---

## 验收原则(所有迭代通用)

1. **结构化断言优先**: LLM 输出是非确定的,角色名/具体话术每次跑可能不同。所有验收只断言"结构属性"(团队规模、必填字段、工具列表是否包含某类),不断言具体字符串。
2. **进阶累加**: Iteration N 的所有用例,都要包含 Iteration N-1 的全部验收点(避免新功能上线破坏老功能)。
3. **真 LLM、真工具**: 不允许用 mock 跑通验收;每个迭代验收必须用真实的 LLM 服务和真实的 tool 执行。
4. **人工确认部分**: 涉及"角色名是否合理"这类创意判断的,放到人工 review 环节,不强求自动化。

---

## Iteration 0 — HR 真 LLM 驱动招募

### 目标能力

HR 能根据**任意** mission 目标真分析并招人,不再依赖关键词匹配。即使输入"完全没在 keyword rules 里出现过"的目标,也能给出合理团队。

### 前置条件

- ✅ `docs/superpowers/specs/2026-05-13-hr-llm-driven-design.md` 完整实施
- ✅ 关键词路径 `team-planning.ts` 删除
- ✅ LLM 服务可用(`@digitalagent/runtime/LlmService` 配置好)

### 用例 V0-1:成语接龙基础协作

**输入 mission goal**:

> "5 个 agent 协作玩成语接龙,每个 agent 轮流给出下一个成语,完成 50 次接龙才算成功。"

**自动化验收点**:

- ✓ Mission 能被创建且 Owner Agent 走完 brief 确认流程
- ✓ Owner Agent 基于已确认 brief 生成 MissionPlan
- ✓ MissionPlan 能被确认,确认后再触发 HR 招募
- ✓ HR Agent 进入 running 状态,日志显示"正在基于 MissionPlan 分析团队需求..."
- ✓ HR Agent 最终进入 idle 状态(不是 failed)
- ✓ 招出的团队规模在 2-5 个角色之间(`preferredTeamSize` 范围)
- ✓ 每个角色都有非空 `name` / `responsibility` / `budget` / `allowedTools`
- ✓ Mission 可激活进入 running 状态(同步激活接口返回 200;异步激活接口返回 202 并能观察到 HR 招募中状态)
- ✓ 团队中**不存在**"Mission Operator Agent"(兜底角色) — 因为关键词路径已删

**人工确认点**:

- ✓ 角色名字与"接龙 / 文字游戏 / 词汇"等主题相关(不是 Generic Worker / Mission Operator 这种泛角色)
- ✓ 至少一个角色的 responsibility 提到"接龙规则"、"成语判定"、"轮次推进"等

**失败信号**:

- ❌ 团队里出现 Mission Operator → 说明 HR 没分析就走兜底了(或者 fallback 没删干净)
- ❌ HR 状态 failed → LLM 真挂了 / prompt 设计不合理
- ❌ 团队规模 <3 → HR 没理解"5 个 agent 协作"的语义

## Iteration 1 — Agent协作能力

### 目标能力

Agent 之间能通过**共享文件**传递中间结果,而不是只靠消息总线。这是测试**工具调用是否真实生效**的第一道关。

### 前置条件

- ✅ Iteration 0 通过
- ✅ Runtime 层接入 `file_read` 和 `file_write` 工具
- ✅ HR LLM prompt 能根据 mission goal 推断需要哪些工具(已有,只需验证)
- ✅ Agent 执行任务时能真实调用这两个工具(不是 mock)

### 用例 V1-1:成语接龙 + 文件读写

**输入 mission goal**:

> "5 个 agent 协作玩成语接龙,每轮把当前接到的成语写入 chain.txt 文件,下一个 agent 必须先读 chain.txt 拿到上一个成语,再接龙写回。完成 15 次才算成功。"

**自动化验收点(包含 V0-1 全部)**:

- V0-1 所有验收点都通过
- Mission 执行后,`chain.txt` 文件实际存在(产出正确)
- `chain.txt` 内容数量为15个，且都是成语(说明轮协作结果正确)
- `Agents` tab页，可以看到每个agent的产出

**人工确认点**:

-  `chain.txt` 中的内容是合法成语(不是 agent 编的字)
-  文件内容呈现"接龙关系"(后一个成语的首字 ≈ 前一个的尾字)
-  HR 招出的角色里,**不是所有角色都用 file 工具** — 通常只有 1-2 个负责"记账",其他负责"出招"

**失败信号**:

- `chain.txt` 不存在 / 是空 → 工具调用没真实发生,可能 runtime 没接好
- `chain.txt` 内容数量错误，或者存储顺序不符合 agent 输出顺序

## Iteration 2 — 网页搜索能力

### 目标能力

Agent 能调用**外部信息源**(网页搜索),把搜索结果纳入决策。验证 runtime 的外部 IO 能力。

### 前置条件

- ✅ Iteration 1 通过
- ✅ Runtime 接入 `web_search` 工具(可调真实搜索接口)
- ✅ Agent 执行结果能携带搜索引用(URL + 标题 + 片段)

### 用例 V2-1:成语接龙 + 出处考证

**输入 mission goal**:

> "5 个 agent 协作玩成语接龙。每接一个成语,其中一个 agent 必须查网络给出这个成语的出处(古籍名 + 大致年代 + 原文片段),附 URL。完成 30 轮才算成功(考虑搜索更慢,减少轮次)。"

**自动化验收点(包含 V1-1 全部)**:

- ✓ V1-1 所有验收点都通过
- ✓ 招出的团队中,**至少一个角色**的 `allowedTools` 包含 `web_search`
- ✓ Mission 执行后,artifact 中至少包含 5 条带 URL 的引用
- ✓ URL 格式合法(以 `http://` 或 `https://` 开头)

**人工确认点**:

- ✓ 引用的 URL 真实可访问(不是 LLM 幻觉出的假 URL)
- ✓ 古籍名 / 年代信息可信(抽查 3-5 条)
- ✓ HR 招出的角色里,"出处考证 / 检索"角色与"接龙出招"角色是**分开**的(说明 HR 真的拆了职责)

**失败信号**:

- ❌ 招出的团队没有 `web_search` 工具 → HR 没识别"查网络"需求
- ❌ artifact 里 URL 全部相同 / 全部假 → 搜索没真实调用,LLM 在编
- ❌ 一个 agent 包揽所有职责 → HR 没做职责拆分

## Iteration 3 — 记忆系统

### 目标能力

**跨 mission** 保留信息。新 mission 启动时,agent 能"记得"上次相关 mission 留下的状态。

### 前置条件

- ✅ Iteration 2 通过
- ✅ 记忆模块上线(具体形态待定:向量库 / KV / 共享文件)
- ✅ Agent 启动时能拿到"过去相关上下文"(可能由 HR 在团队设计时注入)
- ✅ Mission 结束时能写回记忆

### 用例 V3-1:成语接龙 + 记忆延续

**操作流程**:

1. 跑一次"标准成语接龙 mission"(参考 V0-1),完成 50 次后保留 artifact
2. 24 小时后(或代码注入快进),启动**第二个新 mission**:目标 = "接着上次的成语接龙继续,再接 50 次"
3. 不告诉第二个 mission 上一次接到了什么(只给 goal 文字)

**自动化验收点(包含 V2-1 全部 + 跨 mission)**:

- ✓ V2-1 所有验收点都通过
- ✓ 第二个 mission 的初始 artifact / messages 中,包含上一次最后一个成语(说明记忆被注入)
- ✓ 第二个 mission 的第一轮接龙输出的成语,首字 ≈ 上次最后一个成语的尾字

**人工确认点**:

- ✓ 第二个 mission 没有"从零开始"的迹象(比如又把规则重新讲一遍)
- ✓ 记忆引用方式自然(不是把整个上次记录 dump 给 agent)

**失败信号**:

- ❌ 第二个 mission 完全不知道上次 → 记忆没读到 / 没写入
- ❌ 第二个 mission 把上次的角色名也复制过来了 → 记忆粒度过粗,泄漏了不该有的信息
- ❌ 第二个 mission 的接龙完全和上次脱节 → 记忆模块只是摆设

后续可能的迭代(等当前迭代收敛再拆细):


| 迭代  | 能力        | 用例草稿                                    |
| --- | --------- | --------------------------------------- |

## 迭代依赖关系

```
V0 (HR LLM 化)
  ↓
V1 (文件 IO)
  ↓
V2 (网页搜索)
  ↓
V3 (记忆系统)
  ↓
V4-V7 (并行可选)
```

V0 是所有后续迭代的前置 — 因为后续每一项能力都需要 HR 真的能"读懂目标 + 招对工具",这是 LLM 驱动才能做到的事。

---

## 失败时的处理流程

任何一个迭代用例失败:

1. **不要"调宽验收标准"** — 失败说明能力没就绪,而不是验收太严
2. 用 `superpowers:systematic-debugging` 定位根因
3. 修完之后**完整跑一次该迭代所有用例**,不只跑失败的那个
4. 修完后回归 V0..V(N-1) 全部用例,确认没把老功能弄坏
